# SDK 集成决策框架

本文定义集成 Nexconn IMLib 的五层决策流程，用于系统评估实现路径，并以满足需求的最优方式实现。

## 决策流程概览

编写集成代码前，按从上到下的顺序评估五层路径。只有上一层无法满足需求时，才进入下一层。

## 第 1 层：评估 IMKit 原生能力

目标是优先采用成本最低、开箱即用的方案。检查 IMKit 文档是否已有满足需求的界面、API、组件或配置，并确认目标平台可用。若满足，直接集成；否则进入第 2 层。

## 第 2 层：评估 IMKit 定制与扩展能力

IMKit 没有直接功能时，先检查是否能通过扩展点间接实现，而不是立即降级到 SDK。常见扩展包括自定义视图/组件、事件回调和生命周期 hook、主题和样式覆盖、配置项和功能开关、slot 与 render props。若扩展点可满足需求，继续留在 IMKit 生态中；否则进入第 3 层。

## 第 3 层：评估 IMLib API 层

当 IMKit 及其扩展无法满足需求时，检查底层 IMLib 是否提供低层能力。可以直接调用 SDK API、与现有 IMKit 组件组合，或在 IMKit 之上构建补充层。实现时明确标注这是补充实现，便于维护；若仍不满足，进入第 4 层。

## 第 4 层：评估修改源代码

如果 SDK 也没有官方接口，评估修改 IMKit 源代码的可行性：技术可行性、影响范围、升级维护成本以及稳定性/安全风险。

执行步骤：

1. 评估技术可行性和风险。
2. 向用户说明为何前三层无法满足、具体修改点、影响范围、维护成本和升级风险。
3. 明确询问用户是否接受修改源代码。
4. 在用户明确回复前暂停，不得直接修改源代码。

## 第 5 层：最终决策

### 分支 A：用户批准修改源代码

从 [IMKit 源码仓库](./imkit-repositories.md) 获取目标平台源码，在本地或团队 Fork 中开发、测试并实现。交付变更说明，包括修改文件和位置、每项变更原因与逻辑，以及未来版本升级注意事项。

### 分支 B：用户不批准修改源代码

寻找不改源码的替代方案：调整产品设计、使用应用层包装模拟相近结果，或探索原生平台能力/WebView 注入。说明权衡和限制，获得同意后再实现。

### 分支 C：没有可行方案

明确告知当前 SDK 版本无法实现，说明技术限制，并建议联系 [融云技术支持](https://www.rongcloud.cn/contact-us)、调整需求以使用现有能力，或等待未来 SDK 版本。

## 使用建议

始终从第 1 层开始，不跳过层级。记录已评估的层级、前面层级为何不足、最终采用的层级，以及第 3/4 层方案的维护事项。稳定性和可维护性优先，源码修改只能作为最后手段；任何源码修改或替代方案都必须透明说明并获得批准。
